====================================================================
 HOW TO RUN SLM ASSISTANT v3  (read this top to bottom, in order)
====================================================================

This project currently has these pieces:

  1. Database    (Postgres, runs inside Docker)
  2. Redis       (runs inside Docker) - powers the FAQ answer cache and
                  question-frequency ranking (see Part I). Per-user/IP
                  rate limiting is a separate, still-unused use case for it.
  3. Vector DB   (Chroma, runs inside Docker)
  4. Adminer     (Postgres web UI, runs inside Docker) -> http://localhost:8081
  5. Speech      (Python speech recognition for recitation practice,
                  runs inside Docker)                   -> http://localhost:8001
  6. Backend     (NestJS, TypeScript)          -> http://localhost:4000
  7. Frontend    (Next.js App Router)          -> http://localhost:3000

Both the backend and frontend run on your host machine via Turborepo
(`turbo dev`), NOT inside Docker. Only the five services above run in
Docker. Phase 3 of the roadmap will containerize the app itself and
move everything to Kubernetes — until then, this is the setup.

--------------------------------------------------------------------
 ONE .env FILE, AT THE PROJECT ROOT
--------------------------------------------------------------------
There is exactly one `.env` file, in the project root (slm-assistant-v3/.env),
gitignored. Both `docker-compose.yml` and `apps/api` read from it (the api
loads it explicitly via `apps/api/prisma.config.ts` and `app.module.ts`,
since its working directory is `apps/api`, two levels below root).

`apps/web` is the one exception: Next.js only reads `apps/web/.env.local`
(not the root file), and it only needs one variable —
`NEXT_PUBLIC_API_URL=http://localhost:4000` — which is already there.

.env is already filled in with working local values EXCEPT the Google
OAuth client, which is already set up too (see Part F) — there is
nothing left to fill in for local dev.

--------------------------------------------------------------------
 PART A - FIRST TIME ONLY (already done on this machine)
--------------------------------------------------------------------

A1. Install Docker Desktop, open it, wait for it to fully start.
A2. From the project root: `npm install` (installs all three
    workspaces: apps/api, apps/web, packages/shared-types).
A3. `docker compose up -d`
    The FIRST run also builds the speech service image: it downloads
    PyTorch and the Quran speech model and converts it, which takes
    10+ minutes and ~1 GB of downloads. Later runs reuse the image.
A4. `cd apps/api && npx prisma migrate dev` (creates/updates tables)

That's it for one-time setup. From now on, every session, you only
need Part B.

--------------------------------------------------------------------
 PART B - EVERY TIME YOU WANT TO WORK ON THE PROJECT
--------------------------------------------------------------------

One terminal, from the project root:

      docker compose up -d
      npx turbo run dev

This starts postgres/redis/chroma/adminer (Docker, `unless-stopped` —
they usually auto-start with Docker Desktop after a reboot, but
running this is harmless either way) and both apps/api (port 4000)
and apps/web (port 3000) via Turborepo.

Give the api ~60-90 seconds the first time — it type-checks the whole
LangChain dependency tree, which is slow. After a reboot, or the first
start in days, it can take several MINUTES (cold disk cache + slow
drive; even `npx` can take a minute just to launch turbo). That is
slow, not stuck. Watch the terminal for:

      [Nest] ... LOG [NestApplication] Nest application successfully started

Then open http://localhost:3000 — you'll be redirected to /login if
you're not already signed in.

If you open the page before the api is up, you'll see a "Waiting for
the API..." screen that reloads itself every 3s until the api is ready,
and the web log prints this line (expected, NOT an error):

      [web] API not reachable at http://localhost:4000 yet - still starting?

The same brief message appears whenever you save an api file, while
nest restarts. Only worry if "successfully started" never shows up -
then look for a real error in the @slm/api:dev lines above it.

--------------------------------------------------------------------
 PART C - HOW TO STOP EVERYTHING
--------------------------------------------------------------------

Ctrl+C the `turbo run dev` terminal to stop api/web.

      docker compose stop

Stops the Docker containers but keeps all data (Postgres rows,
Chroma vectors). Next time, `docker compose up -d` again — no need to
redo migrations.

To fully wipe the database and vector store and start clean (rarely
needed): `docker compose down -v`

--------------------------------------------------------------------
 PART D - IF YOU CHANGE apps/api/prisma/schema.prisma
--------------------------------------------------------------------

      cd apps/api
      npx prisma migrate dev --name describe_your_change
      npx prisma generate

Run BOTH. Since Prisma 7, `migrate dev` no longer regenerates the
client, so skipping `generate` leaves the database updated but the
TypeScript types stale ("Property 'yourNewModel' does not exist on
type 'PrismaService'").

Always glance at the generated migration file in
apps/api/prisma/migrations/ before trusting it — autogenerate is good
but not perfect.

--------------------------------------------------------------------

Open http://localhost:8081 and log in with:

    Password:  slm

--------------------------------------------------------------------
 PART F - GOOGLE SIGN-IN (already configured, for reference only)
--------------------------------------------------------------------

Uses its own dedicated Google Cloud project ("slm-assistant",
project ID slm-assistant-503922) — NOT shared with any other project.
OAuth client type: Web application, redirect URI already registered:
      http://localhost:4000/auth/google/callback

.env already has the real GOOGLE_CLIENT_ID/GOOGLE_CLIENT_SECRET.
Nothing to do here unless the secret is ever rotated — then update
.env and restart the api.

The first admin is bootstrapped via `ADMIN_EMAILS` in .env (comma-
separated Google account emails). Whichever of those emails logs in
first is auto-promoted to ADMIN — no manual DB edit needed. Everyone
else who logs in becomes a regular USER.

--------------------------------------------------------------------
 PART G - ADDING AN LLM PROVIDER KEY (admin only)
--------------------------------------------------------------------

Log in as an ADMIN -> click "Provider keys" on the dashboard (or go to
/admin/providers) -> pick a provider (GROQ / AZURE_OPENAI / ANTHROPIC),
give it a label, paste the real key -> Add key. Keys are encrypted
(AES-256-GCM) before they ever touch Postgres — verified by inspecting
the raw DB row during Phase 1 testing. Regular users just see a
provider dropdown in the chat panel populated from whatever admins
have added; they never see the raw keys.

--------------------------------------------------------------------
 PART H - RUNNING THE TESTS
--------------------------------------------------------------------

      cd apps/api
      npm test                  (125 tests, ~15s)
      npm run test:cov          (adds a coverage report)

Nothing needs to be running first — no Docker, no dev server, no
network, no provider API key. Every external dependency (Chroma,
Redis, Postgres, the LLM) is faked, so this works on a cold machine
and in CI. Specs live next to the code they cover, as *.spec.ts.

  document-chunker.spec.ts       chunking: headings, word budget,
                                 overlap, chunk ids, empty input
  vector-store.service.spec.ts   the per-file retrieval cap
  faq.service.spec.ts            Redis cache keys + invalidation
  chat.service.spec.ts           the whole RAG pipeline
  features.spec.ts               feature flags + the 404 feature guard
  audio-format.spec.ts           audio type detection from file bytes
  reference-input.spec.ts        surah / ayah-range validation

Two things to know before you edit a spec:

- Do NOT import a Prisma-backed service into a unit spec without
  stubbing it. The generated Prisma client sits in apps/api/generated/,
  which is outside jest's rootDir (src), so it never gets compiled and
  the suite dies with "Cannot use import statement outside a module".
  chat.service.spec.ts shows the fix — one jest.mock() line at the top.

- After changing retrieval behaviour, break it on purpose once and
  confirm a test actually fails. Some chunker properties still pass
  even when heading detection is disabled, because the heading-merge
  step reassembles the text either way. The test that genuinely pins
  section boundaries is "starts a new chunk at a heading even when the
  budget has room left".

Note `npm test` does NOT touch dist/, so unlike `npx nest build` it is
safe to run while the dev watcher is going (see PART L).

--------------------------------------------------------------------
 PART I - FAQ CACHE (Redis) & THE "FREQUENTLY ASKED" TAB
--------------------------------------------------------------------

Every chat question is normalized (lowercased, trimmed, punctuation
stripped) and its ask-count tracked in a Redis sorted set. The sidebar's
"Frequently Asked" tab lists the top questions by that count, ranked by
real usage. Clicking one sends it through the normal chat flow.

Before a question touches Chroma or an LLM provider, the api checks
Redis for a cached (provider, normalized-question) answer. On a hit it
returns instantly - no vector search, no LLM API call - and the chat
UI shows a "cached" badge on that reply. Answers carry a 6h TTL, but
uploading or deleting ANY document also bumps a Redis version counter
that instantly invalidates every previously cached answer, so a
knowledge-base change can never leave a stale answer live.

Admins can delete a junk entry (e.g. someone typed "yes" as a message
and it got tracked) directly from the tab - a Delete button appears on
each row for ADMIN accounts only. This only removes it from the
ranking; it doesn't clear the underlying answer cache.

To inspect the cache directly:
      docker compose exec redis redis-cli KEYS "faq:*"
      docker compose exec redis redis-cli ZREVRANGE faq:counts 0 9 WITHSCORES

--------------------------------------------------------------------
 PART J - PROVIDER USAGE BADGES (rate-limit %, not billing balance)
--------------------------------------------------------------------

The chat panel shows a colored badge per provider (e.g. "GROQ 82%
left") next to the provider dropdown. This comes from the rate-limit
response headers Groq/Azure/Anthropic attach to every real API call
(x-ratelimit-* / anthropic-ratelimit-*) - captured via a custom fetch
wrapper passed into each LangChain client, since invoke() itself
doesn't surface response headers. It updates passively: only providers
you've actually sent a chat message to (since the api last restarted)
have data; others show "-".

This is rate-limit headroom, not a dollar-credit balance - none of
these providers expose per-key billing balance via API. Some
deployments (e.g. Azure OpenAI's Model Router) don't return
rate-limit headers at all, in which case the badge legitimately stays
"-" forever for that provider; that's not a bug.

--------------------------------------------------------------------
 PART K - MANAGING USERS (admin only)
--------------------------------------------------------------------

Log in as an ADMIN -> click "Users" on the dashboard (or go to
/admin/users) -> a table of every user (email, name, role, joined
date) with a Delete button per row.

You cannot delete your own account (blocked server-side; the button is
just hidden client-side on your own row, showing "You" instead). If a
deleted user had uploaded documents or added provider keys, those
records survive - Document.uploadedBy / ProviderCredential.createdBy
just become null (see the nullable_user_owner_fks migration). Deleting
an ADMIN isn't permanent either: they're re-promoted automatically the
next time they sign in with Google, per the ADMIN_EMAILS allowlist.

Also on the dashboard for admins: "Features" - on/off switches for
optional features, currently just Recitation practice (see PART M).

--------------------------------------------------------------------
 PART L - KNOWN GOTCHAS HIT DURING DEVELOPMENT (fixed, but good to know)
--------------------------------------------------------------------

- If the Recitation page shows "Processing..." after you click
  Reprocess, that's normal - it switches to Ready by itself. The match
  percentage is hidden until the new run finishes.

- The speech container runs with `init: true`. Without it, stopping the
  container mid-transcription once left the server process a zombie
  that Docker couldn't kill, and the forced cleanup briefly disrupted
  the other containers. At the same moment the api (in the turbo
  terminal) exited; restarting Redis and Postgres did NOT reproduce
  that, so the cause is unconfirmed. If the api is ever down while its
  watcher is still running, save any file under apps/api/src to make
  the watcher restart it, and check the terminal for the error above
  the point where it stopped.

- `docker build` / `docker compose up --build` can fail with "frontend
  grpc server closed unexpectedly". That's Docker Desktop's build
  engine hiccuping, not the Dockerfile - just run the same command
  again.

- The Redis service now has an explicit `command:` (noeviction, because
  the job queue relies on Redis never dropping keys). The first
  `docker compose up -d` after this change recreates the Redis
  container once. Its data volume is kept, so the FAQ cache survives.

- The local embedding model (Xenova/all-MiniLM-L6-v2, used to embed
  uploaded documents for Chroma) downloads once on first use to
  node_modules/@huggingface/transformers/.cache/. If that download
  ever gets interrupted (laptop sleep/shutdown, flaky network), you'll
  see "Protobuf parsing failed" on upload. Fix: delete
  node_modules/@huggingface/transformers/.cache/ and retry the upload
  — it re-downloads (~90MB) automatically.

- Uploaded documents are stored on disk at apps/api/data/docs/, which
  is excluded from the TypeScript watcher (apps/api/tsconfig.build.json
  "exclude") — this was a real bug earlier (every upload was triggering
  a dev-server restart that killed the upload's own request). If you
  ever add another runtime-writable directory under apps/api, exclude
  it the same way.

- Access tokens (httpOnly cookie) last 60 minutes. If you get bounced
  back to /login unexpectedly, that's just the session expiring — sign
  in again, it's instant since Google still remembers you.

- On Windows, `nest start --watch` occasionally crashes on its own
  restart cycle (`ERROR: The process "<pid>" not found` /
  `taskkill /pid ... /T /F` failing, sometimes followed by
  `Cannot find module .../dist/main`). This is nest-cli's Windows
  process-tree-kill racing itself, not a code error — Found 0 errors
  usually appears right before it happens. Fix: just re-run
  `npm run dev` in apps/api. Also avoid running `npx nest build`
  manually while `--watch` is active — it writes to the same dist/
  folder the watcher depends on and can trigger this same crash.

--------------------------------------------------------------------
 PART M - RECITATION PRACTICE (optional feature, OFF by default)
--------------------------------------------------------------------

Status: phases 1-2 of 5 - upload a reference recitation; it is aligned
to the Quran text automatically, and clicking any word plays exactly
that word. Checking YOUR recitation comes in phase 3 (see README).

Turn it on: sign in as ADMIN -> "Features" -> switch on "Recitation
practice". An "Assistant | Recitation" switcher then appears in the
header for everyone. Switching it off hides the tab AND makes the api
answer 404 on every /recitation route - the toggle is enforced on the
server, not just in the UI.

Upload: pick an audio file (MP3, WAV, FLAC, OGG/Opus, M4A, AAC, WebM,
up to 100 MB), the surah number, and optionally an ayah range. Any
signed-in user can upload; only admins can delete.

Worth knowing:
- The file type is detected from the file's bytes, not its extension,
  so a renamed PDF is rejected even if it's called "quran.mp3".
- Files are stored at apps/api/data/recitations/ under generated uuid
  names (the original filename is kept only for display). That folder
  is gitignored and excluded from the api watcher, like data/docs/.
What happens after upload:
  "Queued" -> "Processing..." -> "Ready · 93% of words matched"
The page updates by itself. Behind it: a background job (BullMQ, on
Redis) sends the file to the speech service container (port 8001),
which transcribes it and aligns every word to the Quran text. Then
"Show words" lists the vowelled text; click a word to hear it.

Speed on THIS laptop (Core i3-7100U, 2 cores): about real time, e.g. a
36 s surah takes ~36 s. A long surah takes as long as its recording.

If a recitation shows "Failed":
- "Speech service unreachable" - the speech container isn't running.
  `docker compose up -d`, then click Reprocess (admin).
- "Only N% of the expected words were recognised" - usually the wrong
  surah number or ayah range for that file. Delete and re-upload with
  the right numbers.
- Failed jobs retry automatically 3 times (15s, 30s apart) before
  showing Failed; a wrong ayah range fails at once, since retrying
  can't fix it.

Speech service checks:
  curl http://localhost:8001/health      (model revision, verse count)
  docker compose logs -f speech          (one line per processed file)

Tuning (docker-compose.yml, speech service `environment:`):
- CPU_THREADS: set to your PHYSICAL core count (2 here). Using all 4
  threads, including hyperthreads, was 2.2x SLOWER on this CPU.
- OMP_NUM_THREADS / OPENBLAS_NUM_THREADS / MKL_NUM_THREADS: keep these
  equal to CPU_THREADS. Left unset, the audio-feature code starts one
  thread per logical CPU on top of the decoder's; one run hit 400% CPU
  and took 326 s for a 36 s file (86 s with them capped).
- BEAM_SIZE: 5 by default; 1 decodes about twice as fast.

If the speech container shows "unhealthy" while processing, give it a
minute: transcription uses every core, and the health check is
deliberately lenient about that.

After changing anything under services/speech/app:
  docker compose up -d --build --no-deps speech
Run its tests (inside Docker, ~1 min):
  docker build --target test services/speech
